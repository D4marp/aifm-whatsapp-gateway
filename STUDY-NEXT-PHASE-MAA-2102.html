MAA-2102 next phase: implementation and safety study

Request

A standalone .NET system with its own SQL Server database that manages incoming and outgoing messages (text, audio, video) for several WhatsApp numbers, with API methods so other web systems can post outgoing messages and read incoming ones.

What the POC already covers

PartStatus
Own SQL Server database with outbox and inbound tablesDone, text only
API to queue a message and to read incoming messagesDone in the lab, no authentication yet
Pacing: send hours, daily cap, wave limit, gap, random jitterDone, for one number
Swappable WhatsApp connector (an interface with a fake and a real one)Done
Several numbers at the same timeNot done: one number is one browser profile and one worker
Audio and videoNot done

Running on a serverNot tested

Target design

The ERP becomes one client of the API. Each number has its own worker, login and pacing. Messages and results go through the database, so a worker restart does not lose queued messages.

Implementation notes (proposed, not built yet)

RequirementHow
Several numbersSession table (number, state, login location, settings). One worker per session with its own login folder or auth state, own pacing and daily cap. QR login per number from the dashboard or API. Never the same number in two places
Send mediaOutbox row points to a media record. The worker uploads the file through the connector. Size and type limits
Receive mediaThe worker downloads the file and stores it outside the database (disk or blob). The database keeps type, size, hash and path. Failed downloads are retried and flagged
Post outgoingPOST with number, target group or contact, text or media id and an optional idempotency key. Returns an id. GET status: Pending, Sent, Failed
Read incomingGET incoming after a cursor, filtered by number. The client confirms what it processed, so nothing is read twice or lost. Webhook as a later option
Process layoutWorkers run as their own service, not inside the ERP. The API stays up when a worker restarts

Safety: account (ban risk)

What the sources say: WhatsApp's Terms of Service name bulk messaging, auto-messaging and automated account creation as prohibited. The Messaging Guidelines (updated 23 Sep 2026) list unofficial clients, bulk messaging and automation under adversarial behaviour, with the qualifier "to harm WhatsApp or our users", and say an account can be suspended temporarily or permanently. Both connector types are unofficial, so neither removes the risk. Vendor articles say bans are often abrupt and without warning; they come from companies that sell the official API, so treat them as indicative only. No public rule on safe send rates was found. The POC settings (10 to 15 a day, waves) come from team advice and are not verified.

MeasureWhy
Use dedicated numbers, not personal numbersA ban then costs only that number (POC lesson: the linked number was personal)
Send only to groups and people who expect messagesThe Guidelines name repeated unwanted contact as spam
Pacing per number: hours, daily cap, wave, gap, jitterAvoids machine-like bursts (implemented)
One worker per number, no second login of the same numberAvoids conflicting sessions
Do not open and close the connection in quick cyclesOne vendor article lists it as a suspicious pattern (single source)
Kill switch per number; pause automatically on logout or repeated failuresStops before damage grows
Monitor sends, failures and logouts per numberFinds problems early

Safety: the system

AreaMeasure
API accessAPI key per calling system, stored hashed, limited to its allowed numbers. HTTPS. Rate limit per key
Login materialThe browser profile or auth state is the key to the account: encrypted disk, restricted access, never in git, zips or shared backups
SecretsConnection strings and keys outside the repository (vault or environment)
Private dataGroup messages are private. Per-number allow list of groups to read (POC lesson: receiving stored messages from an unrelated group), retention period, access log
Media filesSize and type limits, malware scan, never executed, stored outside the web root
AuditLog who posted what, to which number and when. Message content is not written to application logs
ResilienceThe outbox lives in the database; a worker crash loses nothing; retry up to 3 times (implemented)
